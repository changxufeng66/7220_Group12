# 接力规则

这个仓库的核心玩法就一个词：**接力**。别人做了一半的东西，你要能直接接上；
你做到一半的东西，别人也要能直接接上。难点不在 git，在**交接时有没有把话讲清楚**。

---

## 一、每份作业两个文件，各管一件事

| 文件 | 写什么 | 特点 |
|------|--------|------|
| `README.md` | 题目、要求、截止时间、验收标准、当前总状态 | 稳定，不常改 |
| `接力记录.md` | 谁在什么时候做了什么、下一步交给谁 | 只追加，不改历史 |

**为什么分开？** 因为两个人同时改同一段文字才会冲突。把「稳定信息」和「追加流水」
拆开，绝大多数并发修改都能自动合并成功。

---

## 二、`接力记录.md` 的格式

```markdown
| 日期 | 谁 | 做了什么 / 下一步 | 状态 | PR |
|------|-----|------------------|------|-----|
| 2026-11-06 | 张三 | 搭好框架，第 1、2 题做完 | 进行中 | — |
| 2026-11-07 | 张三 | 第 1、2 题完成，第 3 题推到一半；**下一步：李四 接第 3 题** | 待接手 | #12 |
| 2026-11-07 | 李四 | 接手第 3 题 | 进行中 | — |
```

### 状态只用这 5 个词

| 状态 | 含义 |
|------|------|
| `未开始` | 还没人碰 |
| `进行中` | 有人正在做 |
| `待接手` | 上一个人暂停了，缺人继续（**必须在同一行写清「下一步」**） |
| `待评审` | 做完了，PR 已开，等人看 |
| `已完成` | PR 已合并，可以交作业了 |

不要自己发明状态词，否则别人看不懂。

---

## 三、动手前必做：占位

**在写任何作业内容之前**，先在 `接力记录.md` 加一行：

```markdown
| 2026-11-07 | 王五 | 接手：第 2 题公式推导 | 进行中 | — |
```

这一行的作用是**广播**：「这块我在做，别动」。顺序很重要——先占位，再动手。
如果两个人几乎同时占了同一块，看到记录后协商一下，谁改一下范围就行，
这比事后合并冲突便宜得多。

---

## 四、交接时，把「上下文」写下来

一个合格的交接，看记录的人应该能不问你就继续干。所以「下一步」那一格至少写清三件事：

```
下一步：李四 接第 3 题的数值实验
  · 代码在 src/exp3.py，跑 python exp3.py 会输出 results.csv
  · 卡住了：lr 设成 0.1 会发散，怀疑是归一化没做
  · 还没做：把结果画成图放进报告
```

**宁可写多，不要写少。** 你省下来的 5 分钟，会变成别人 30 分钟的重猜。

特别要写清楚的：

- 卡在哪、你试过什么、为什么不行（避免下一个人重走一遍）
- 有哪些「看起来能用但其实没验证」的地方
- 谁的哪部分依赖你的输出（改了会影响谁）

---

## 五、半成品也要提交

不要因为「还没做完」就不提交。**做完 60% 的提交，比没提交的 100% 有用。**

- 小块多次提交，push 到自己的分支，随时可被别人接手
- 只想给别人看、暂时不合并的，PR 里标注 `[WIP]`（Work In Progress），或者留着分支不合
- 真的做不下去：把分支 push 上去，`接力记录.md` 写 `待接手` + 说明卡点，然后开个 Issue 挂出来

---

## 六、两个人同时改一份作业怎么办

1. **先看 `接力记录.md` 最后一行**——大概率已经有人占了
2. 没人占但你想改同一段：把工作拆细（「我在第 3 题，你去第 4 题」）
3. 已经撞了：谁的分支还没 push，谁就 `git pull` 后重来一遍，代价最小
4. **二进制文件（docx/pptx）绝不允许两人同时改**，见 README 第五节

---

## 七、合并的礼貌

- review 别人的 PR 时，说「这里为什么这么做」而不是「这写错了」
- 合并后用 **Squash and merge**，别在 `main` 上留一堆 "update"、"再改一下"
- 合并完记得回来把 `接力记录.md` 的状态改成 `已完成`
